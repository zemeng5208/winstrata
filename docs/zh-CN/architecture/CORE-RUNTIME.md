# Core 调度与事件总线

[English](../../architecture/CORE-RUNTIME.md) · [Rust 库](../../../core/src/lib.rs) · [计划 007](../roadmap/PLAN.md#pr-007)

计划 007 在 `winstrata-core` 中加入固定工作者池和进程内事件总线。`Core::open` 不会启动它们。需要任务或订阅时调用 `Runtime::start`，结束时调用 `shutdown` 或丢弃运行时以汇合线程。尚未批准异步运行时依赖，因此本次使用 Rust 标准库。若要替换该选择，须单独申请依赖。

## 上限

`Limits::standard` 使用 2 个工作者、256 个任务队列、1,024 个事件队列、1,024 个共享事件名额、64 条批量、64 个订阅和 20 毫秒准入等待。`Limits::check` 拒绝零值，也拒绝超过固定天花板的值：32 个工作者、65,536 个任务或事件、1,024 个订阅、5 秒准入等待，以及大于订阅队列的批量。任务超时必须大于零且不超过 24 小时。

这些是本计划的最低保护。动态 CPU、I/O 和内存预算仍由 StrataBudget 负责，诊断展示仍由 StrataHealth 负责。

## 任务

`Scheduler::submit` 接收优先级、超时和闭包。优先级数值较大者先运行，相同优先级按提交顺序运行。调度器保留配置数量的工作者和 1 个计时线程。任务队列已满时，提交最多等待准入时限，随后返回 `queue_full`，该任务不会运行。

`Cancel::cancel` 会移除尚未开始的任务，并设置 `Cancel::is_cancelled` 可见的标志。计时线程在截止时间设置同一标志。运行中的任务必须自行观察该标志。调度器不会强行终止忽略取消的线程；该任务继续占用工作者，关闭调度器时会等待闭包返回。任务 panic 被计数，工作者继续处理后续任务。关闭时取消排队任务、通知运行中的任务，并汇合全部调度线程。

## 事件

`EventBus::publish` 取得协议 `Event` 的所有权。总线先校验事件，再与该来源的游标比较序号。来源接受的第一个序号建立游标。之后的观测必须是下一个序号。缺口标记必须恰好覆盖 `cursor + 1` 到 `sequence - 1` 的开放空洞；标记省略区间时，总线在投递前补上该空洞。紧邻的标记不能携带区间。重复或无效事件连同 `duplicate_sequence` 或 `invalid_record` 退回调用方，跳号的观测连同 `missing_record` 退回。总线不为第一个序号之前的空档补洞，也不因事件时间回退而制造缺口。

每个匹配的订阅方有自己的有界队列，这些队列共同使用 `global_queue`。优先级较高的订阅方先获得剩余共享名额。热路径保存 `Arc<Event>`，不再序列化 JSON。`recv_batch` 的等待时间由调用方给出，且不能超过 5 秒，返回数量不超过配置的批量。

匹配的订阅方暂时无法接收时，发布操作先等待准入时限。等待结束后把该事件记为丢失，而不是无记录地丢弃。单个丢失序号成为占据该序号且不带区间的 `lost` 缺口。连续多个丢失合并为最后一个序号上的缺口，其区间包含前面的序号。类型过滤以同样的形状记录 `filtered` 缺口。生产者自己的缺口标记仍会通过类型过滤。设备或提供方不在订阅范围内时，不记为该订阅方的丢失。丢弃订阅会释放尚未读取的队列，并把这些事件计入 `released`。

总线只传递当前事件。后加入的订阅方不会收到更早的事件，来源标识也不授予权限。带身份认证的传输见[服务 IPC](SERVICE-KERNEL.md)，持久历史属于 PR 012。

## 验证范围

在 Linux x86_64、Rust 1.100.0 和 Intel Xeon 主机上，`cargo test --workspace --locked` 通过了原有 Core、协议测试和本次运行时测试。Release 构建中，调度任务向订阅方发送 20,000 条协议观测，耗时 39.925 毫秒，约每秒 501,000 条，序号连续且无丢失。同一测试的 Debug 运行也在 10 秒界限内完成。测试覆盖准入等待、队列拒绝、合并后的丢失与过滤缺口、跨批次空洞、重复序号、优先级、合作式取消、超时信号、panic 隔离、订阅上限，以及关闭后释放线程。Linux 还确认汇合后的工作者和计时线程 ID 不再带有该调度器的线程名。检查比对记录下的启动时间，并最多等待两秒让内核删除任务项。

本计划尚未在 Windows 上执行，也未验证 Windows 10/11 客户端、长时间压力、GUI 延迟、动态预算和带认证的 IPC。E2E-08 与 E2E-15 仍是后续验收场景。见[工程记录](../records/STATUS.md)。
